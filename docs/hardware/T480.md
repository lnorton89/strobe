This is the owner's real-hardware test machine and the reference "old

| | |
|---|---|

| OS | Windows 11 Pro, build 26300 |
| CPU | Intel Core i7-8550U, 4 cores / 8 threads |

| Display | One internal panel, 2560×1440 @ 59 Hz, Windows scaling to 1707×960 logical |

**This driver matters.** Intel UHD 620 on driver 30.0.101.1122 is the
exact combination that rustaman documented taking an access violation
inside `igvk64.dll` (the Vulkan ICD) during swapchain creation. Strobe
doesn't use Vulkan, but this machine is the right place to prove the
WGL path, the ANGLE fallback, and native crash capture (minidumps) on a
driver known to misbehave.

The display is 1440p, so a fullscreen output on this panel means
rendering 3.7 M pixels per frame on an integrated GPU. That makes render
scale and adaptive resolution decisive here, not optional.

### Bug 1: the native app loses its context on SDF Cathedral at full resolution — OPEN (recovery built, cause unconfirmed)

After 13–16 seconds on `09-sdf-cathedral` at 1440x810, two runs out of
two failed with:

```
ERROR strobe: make current: [6] The handle is invalid. (os error 6)
```

The same scene works at render scale 0.5, works on ANGLE at full
resolution, and **works in `strobe-bench --context window` at
2560x1440** (82 ms/frame, no failure). So this is not plain shader cost.
The difference is the app's two-surface present path (make current per
window, swap, vsync) under a 20+ ms GPU frame. The Windows event log
showed no TDR (Display 4101) entry, so a GPU reset is unconfirmed.

Next steps:
- Rerun with `STROBE_GL_DEBUG=1` once the app-integration branch lands
  (GL debug output, structured failures).
- Check `GetGraphicsResetStatus` after the failure.
- Whatever the cause, **the app must survive this**: on a lost or
  unusable native context, recreate it, or fail over to ANGLE, reload
  the scene and keep going. This is built (D66, branch
  `agent/context-recovery`) and verified under Xvfb only.

**To check on the laptop** (build from the recovery branch):

1. Run `strobe --gl auto --no-adaptive --scene 09-sdf-cathedral` at full
   render scale with `STROBE_LOG_STDERR=1` in a console build, or read
   `%LOCALAPPDATA%\strobe\logs`. Run past the 13-16 s where it used to fail.
2. Look for `GL context: robust` (or the refusal) and then, at the failure,
   the `CONTEXT phase=lost` record: it carries the `window`, the error and

### Bug 2: native crash capture never connected on Windows — FIXED

`crash_demo` printed `native capture connected: false` on every run. The
abort and stack-overflow runs left only a `.log`, with no `.txt` and no
`.dmp`, and each run took about 60 s (the monitor's patience for an app
that never connects). The panic report (`.txt`) worked.

Cause: the shared socket helper deleted "stale" socket files before
*every* use, including the app's connection attempts. On Windows and
macOS (path sockets) that deleted the socket the monitor was listening
on. Linux uses abstract-namespace sockets and was unaffected, which is
why it passed in CI. The fix moves the cleanup into a bind-only helper.
**Re-verify on this machine:** `crash_demo abort` and
`crash_demo overflow` should each produce `.txt` + `.dmp` within a few
seconds.

**Attempt 3, 2026-10-09, commit 5367681** (socket under the data dir in
long-path form), with `STROBE_DIAG_DIR` inside the repo:

| Run | Connected | Time | Files |
|---|---|---|---|
| `overflow` | true | 2.5 s | `.dmp` (1,061,479 B) and `.txt`; `exception code 0xC00000FD` |
| `panic` | true | 2.5 s | `.txt` (panic report; no dump, by design) |
| `abort` | true | 2.7 s | `.log` only |

```
0.011s ... connect to C:\Users\ExaltedLaptop2\Development\strobe\target\t480\diag4\run\strobe-crash-17152.sock failed: ... (os error 10061)
0.062s ... connected to crash monitor after 54.9756ms
```

The first refusal is the monitor not yet listening; it connects 50 ms
later. So the pipeline works on Windows: a stack overflow produces a
minidump.

- **`abort` leaves no report, and cannot.** Rust's `process::abort` on
  Windows is `__fastfail`, which terminates without running any
  in-process exception handler; only Windows Error Reporting sees it.
  Release builds use `panic = "abort"`, but the panic hook writes its
  report before the abort, so panics are still covered.
- **Outside the repo it failed only inside the test agent's
  environment.** The agent runs inside the Claude desktop app, an MSIX
  package, and every process it starts inherits that package context,
  with or without the tool sandbox. Windows virtualises
  `%LOCALAPPDATA%` for it (the log showed
  `...\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Local\strobe\run\...`,
  119 bytes, which pushed the socket to the temp-dir fallback). Under
  that redirection, every AF_UNIX connect after the first fails with
  `10022` (`WSAEINVAL`). **The owner ran
  `crash_demo.exe overflow` from an ordinary PowerShell window with the
  default directories, and it printed `native capture connected: true`.**
  Strobe launched normally is unaffected. Crash drills run by an agent
  on this machine must set `STROBE_DIAG_DIR` inside the repo.
- An unconnected monitor used to keep the app's process tree alive for
  its 60 s watchdog (`Start-Process -Wait` waited for it). The app now
  kills the monitor at exit if it never connected.

## Render scale, ANGLE-Vulkan and Synesthesia's scenes on Intel (2026-10-27, commit 6f744d4, Tasks 46-49, D-06, G-05, I-05, C-02)

**Task 46 (D-06): half scale is a real lever on this GPU.** The full

  simulation's.
