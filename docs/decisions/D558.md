# D558: the sandbox generates controls a step per animation frame, on the app's own engine and settings (2026-11-06, owner's request)

**Context.** The owner asked for "a button to autogenerate controls like
strobe can do" in the website's `/play` sandbox (D524). The app's button
(D202) runs `strobe_autocontrol::generate` in a worker process, because
measuring renders a scene dozens of times and a show must not wait. A browser
tab has one WebGL context, on the main thread, and no such worker. The crate
also did not build for the browser: its command line brought clap and glutin,
and `strobe-shadertoy`, which it used for a tokenizer, reaches `strobe-diag`,
the crash handler and `polling`, which has no wasm32 target.

**Decision.**

- **The tokenizer moves down, rather than the importer being cut up.**
  `glsl.rs` and the four marker lines a converted pass file carries move to
  `strobe_scene::glsl`. `strobe-shadertoy` re-exports them, so its code is
  unchanged, and `strobe-autocontrol` takes it as a dev-dependency only, for
  its converted test fixtures. The scene model already assembles GLSL and
  needs nothing new for this. Gating `strobe-diag` inside the importer would
  have left a browser build holding the converter, the asset cache and the
  listener for one lexer.
- **The command line is a default `cli` feature** (clap, anyhow,
  `strobe-gfx/native`). The workspace names the crate with default features
  off, as D524 does for `strobe-gfx`, so the app and `strobe-web` get the
  library alone and the binary still builds by default.
- **The layering stays sound; the rules say more than before.** `strobe-web`
  to `strobe-autocontrol` breaks no rule of D541: both sit above the renderer,
  and nothing below reaches them. Two rules are added so this stays true:
  neither crate may reach `strobe-shadertoy`, `strobe-diag`, `strobe-script`,
  `ureq` or `rquickjs`. CI's `site` verdict gains `strobe-autocontrol`, since
  a change there now changes what the site builds.
- **The pipeline is a state machine, and `generate` is it run to the end.**
  `strobe_autocontrol::Job` holds what the pipeline held on its stack. A
  `Job::step` does one piece: hands a build to the driver, polls it, reads how
  it went, renders one probe (ten frames at 160x90, two read back), or compares
  a result with the original. `generate` calls the same transitions in a
  loop, waiting for a build rather than polling it. There is one path, so the
  two cannot drift (D126). `score::measure` is likewise `Probing` run to the
  end, and `Rig::new` is `Rig::begin` then `finish`.
- **A step per animation frame, after the scene's own frame, and never more
  than half the time.** The page runs the live frame and then a step, and the
  next step waits as long as the last one took (`nextStepAt`). D550 leaves a
  show four fifths of the time on a machine that is playing to a room; a page
  someone just asked to measure takes half. A paused scene holds its picture,
  which `preserveDrawingBuffer` keeps, and the measuring goes on.
- **Compiles do not freeze the page where the browser can help.** A build is
  the longest piece: on ANGLE-D3D11, seconds for a heavy scene (D555). D555
  left the browser on the blocking path, on the belief that WebGL needed the
  extension enabled first. glow enables `KHR_parallel_shader_compile` as it
  wraps the context, so `Gl` now reads the extension's WebGL name too and a
  `Job` polls `COMPLETION_STATUS_KHR` between frames. The page's own live load
  still blocks, as it did.
- **Scoring leaves the live scene alone.** Nothing here draws to the default
  framebuffer. The player binds its target, viewport, program, samplers and
  vertex array before every draw and unbinds at the end, so the two players
  need nothing saved or restored. One thing had to change: a GL error flag
  left by a live frame would have been blamed on the measurement, so a step
  clears the flags first. The driver path does not, and behaves as before.
- **The app's settings, unchanged.** 160x90, 10 frames, 2 captured, at most 40
  candidates, 8 kept. Lower settings would save little and would break "the
  same scene gets the same controls" (D126). A probe is 144,000 pixels, a
  sixth of one frame of a 1280x720 canvas at the same shader. A scene's cost is
  measured below; no phone has been tried yet (W-02).
- **The result comes back as files.** `output::rewritten_files` returns the
  GLSL and the `scene.json` splice `write_scene` writes, which now shares it.
  `Job::with_images` gives the rigs the pictures the page holds (D554), so a
  scene that reads an image is measured with it.
- **What a person sees, following the app.**
  - "Generate controls" beside Save preset in the Controls header, with a
    tooltip, and a line in the panel's empty state for a phone, which has no
    hover. A scene with controls of its own gets "Add generated controls" and
    a merge, as in the app.
  - While it runs: "Scoring 3 of 12", a bar, Cancel. The scene keeps playing.
  - The review is D219's and D246's: each control kept or dropped, renamed, a
    slider re-ranged, grouped, with how much it moved the picture, how
    faithful the defaults are, and the audio ideas. Nothing changes until Add.
    It goes through `rewrite_chosen`, so no measuring and no second truth.
  - Add makes it an edit: the editor shows it, the panel shows the controls,
    and autosave, share links and the zip carry it as they carry any edit.
  - Undo restores only the files the accept changed, so a preset saved since
    survives. If one of those files was edited since, it asks first and names
    it.
- **Never lose what was typed.** Typing stops a run ("You edited the scene")
  and is kept. A review of code that has since changed refuses to apply, as
  D219's does. Measuring reads the editor's text as it is now, not the last
  compile, so a compile error is reported from the first step, on its line,
  and nothing further runs.
- **A script scene is measured as in the app** (D259): the script does not
  run, its uniforms are declared at zero, and the review says so. A scene whose
  uniforms the static scan cannot find fails with that said.

- **"Compiled" now means compiled.** The status line read `Compiled ·
  starting` on first paint, before the engine had loaded. The specs wait on that
  line, so they could press a button while the page had no scene, and Save
  preset then did nothing. That was the real cause of the preset spec's missing
  prompt, which e1105a6 put down to a second worker on Windows; the larger wasm
  made it lose the race every time. The line now says "Starting the engine…"
  until a compile has succeeded, and the spec passes with three workers.

**Trade-off.**

- The wasm grows from 1.20 MB to 1.47 MB (469 KB to 561 KB gzipped), for a
  button most visits will not press. It is one module (D524), and splitting
  it would cost a second instantiation and a second copy of the renderer.
- On a software rasteriser a heavy scene is slow: a probe of
  `12-silicon-atlas` takes about 2.5 s on SwiftShader on LIGHTNING, so 81
  probes with the page's half of the time come to about seven minutes. The page
  stays usable and Cancel works, and a visitor on such a machine was already
  watching this scene at 11 fps. For the same reason CI runs that scene to
  Scoring and Cancel, and runs the whole flow on a lighter library scene with
  its controls baked in.
- The first draw of a freshly linked program can take driver time, which a
  poll does not avoid (D555). A step holds the page for as long as that takes.
- A second program for the scene exists while it is measured. A page already
  near its memory limit could lose its context, which W-02 has not handled.
- A scene with `#include` gets the included code written into the file that
  includes it, as the app's copy does: the analysis reads the expanded text,
  and a candidate may be in the included code. The review says so.
- Measured in the browser, the scene is ES 3.00; in the app it is usually
  desktop GLSL. The engine's tests hold that the dialects agree (D126), not
  that a driver's rounding does.

**Test.**
- strobe-autocontrol (`tests/engine.rs`, headless, CI's Linux job):
  - `a_job_stepped_to_its_end_gives_what_generate_gives_in_both_dialects`;
  - `a_job_says_how_far_it_has_got_a_candidate_at_a_time`;
  - `a_job_dropped_at_any_step_leaves_no_gl_object_behind`, on the new
    `Gl::live_objects`, which the create and delete leaves count.
- strobe-web (`tests/sandbox.rs`, the same context in GLES 3.0):
  - `the_sandbox_proposes_and_writes_what_the_apps_engine_does`: the same
    controls and, byte for byte, the same files as `generate` and
    `rewritten_files`;
  - `generating_between_frames_leaves_the_live_scene_as_it_would_have_been`,
    on a feedback scene, byte for byte;
  - `cancelling_leaves_the_scene_as_it_was_and_frees_what_was_made`;
  - `a_scene_folders_picture_and_the_pages_are_measured_alike`, and tests
    for a merge, a compile error, nothing to offer, a script, and a review
    that drops, renames, re-ranges and refuses a changed scene.
- `tests/unit/play-generate.test.ts`: the progress line, the step spacing,
  what a review sends, and what Undo restores or asks about.
- `tests/e2e/play-generate.spec.ts` in Chromium on SwiftShader, the `site` job:
  the library's scene with no controls (`12-silicon-atlas`) through progress
  with the canvas still changing, then Cancel; `01-aurora-gradient` with its
  controls baked in through review, accept and undo; then cancel and restart, a
  review's edits surviving a reload, a merge, a compile error, nothing to
  offer, a script, and typing during a run, a review and after an accept.
- `strobe-autocontrol --context window --report --dry-run --force-merge` on
  LIGHTNING (RX 580), master against this branch, on `12-silicon-atlas`,
  `02-plasma-pulse`, `06-feedback-trails` and `11-script-orbits`: byte-identical
  reports.
- In headless Chromium on LIGHTNING (RX 580, ANGLE-D3D11), one run each:

  | scene | controls proposed | total | fps during (60 idle) | worst gap |
  |---|---:|---:|---:|---:|
  | `01-aurora-gradient` (beside its own) | 5 | 0.9 s | 60.4 | 17 ms |
  | `04-voronoi-glass` (beside its own) | 2 | 0.9 s | 59.6 | 17 ms |
  | `12-silicon-atlas`, warm | 8 | 3.1 s | 59.6 | 33 ms |

  The first run of `12-silicon-atlas` in a browser, with nothing cached, took
  6.1 s. Its 81 probes had a median of 13 ms and took 1.1 s in all. Compiles were
  polled over tens of frames rather than waited for, and the longest step,
  212 ms, was a first draw. It proposed the same 8 controls under the same names
  and scores as `strobe-autocontrol` on the same GPU's desktop GL.
- On SwiftShader on LIGHTNING, `01-aurora-gradient` took 0.8 s and
  `04-voronoi-glass` 6.3 s at 38 fps. `12-silicon-atlas` was timed for 150 s and
  stopped; it was not run to the end there.
- Measuring a phone, and any browser but Chromium, is left to W-02.

**Would reopen:** a browser whose first draw stalls enough to make the steps
visible, which would argue for an OffscreenCanvas in a worker with its own
context; a need to measure at another size on phones; or the wasm's growth
mattering to the page's load.
