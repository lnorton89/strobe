# D534: the script-aware corpus is a regression gate, with expectations and baseline frames (2026-11-03, engineering audit)

**Context.** CI rendered the scene library through `strobe-bench`, which
does not run scene scripts, so a scene whose uniforms only its script
creates (D62, D161) was never really tested. `strobe-corpus` loads scenes
the way the app does, scripts included, and isolates each scene in a child
process. But it exited 0 whatever the scenes did: its docs called it "a
measuring tool, not a gate". The audit of 2026-10-28 pointed out that
adding it to CI as it stood would have produced a gate that could not
fail. The bench's PNGs were uploaded for a person to look at, and nothing
compared them.

**Decision.**

- **`strobe-corpus --expect <file.json>`** compares the run with a
  committed expectations file: the settings, and each scene's status in
  each dialect. Completeness is two-way. An expected scene that was not
  measured fails (a fixture deleted or renamed), and so does a measured
  scene with no expectation (a new scene nobody wrote down). A status that
  changed fails in either direction. A scene that starts passing is also a
  failure until its expectation is moved, in a reviewed change. A crashed
  or hung worker is a `gl_error` or `timeout` record, so it can never read
  as a pass.
- **Images, for listed scenes only.** Each worker can write its final
  frame as a PNG. The scenes under `images` are compared with
  `<name>.baselines/<scene>.<dialect>.png` in every dialect they are
  expected `ok` in. A pixel counts as changed when a channel moves more
  than 16 levels, and a frame fails when more than 0.5 % of its pixels
  changed. A failure leaves `diff/<scene>.<dialect>/{baseline,candidate,diff}.png`,
  which CI uploads as the `corpus-gate` artefact.
- **Baselines are CI's.** They are what Mesa's llvmpipe draws on CI's
  Linux runner, taken from that artefact. `--bless` rewrites the file and
  baselines from a local run, for a local driver.
- **Two libraries in the `render` lane.**
  `crates/strobe-app/tests/corpus-gate/fixtures/` holds nine original
  fixture scenes:
  - a uniform created in `update` and one created in `setup`;
  - a feedback loop through `syn_FinalPass`;
  - a buffer pass at a third of the size;
  - hard and smooth transitions;
  - a smoothed control;
  - a plain gradient;
  - two scenes that must fail, a shader that does not compile and a
    script that throws.

  `scenes/` runs as well, with three of its scenes imaged. Both run in the
  dev profile: the app smoke step has already built `strobe-app` there, so
  this costs a link, and correctness does not need opt-level 3.
- Each record now carries a hash of its scene folder's files, and each
  report the build's version, commit, profile and target, so a report
  names exactly what it measured and with what.

**Trade-off.** A new library scene needs a line in `library.json`. A change
that moves an imaged frame needs its new baseline from the CI artefact.
That is the point: the change becomes visible and reviewed. A Mesa update
on the runner image could move a frame past the tolerance, and then the
baselines are re-taken in their own commit.

**Test.** `corpus::gate`'s unit tests cover the failure cases: a removed
fixture, a new scene with no expectation, a script-created uniform that no
longer compiles, a crashed and a hung worker, a scene that newly passes,
different settings, an empty run, a frame within tolerance and one past
it (with its diff written), a missing baseline, and bless. On the owner's
Windows desktop, the fixture gate passed in both dialects. With the
`update` script's `setUniform` removed, it failed on
`'tint' : undeclared identifier`.

**Would reopen:** the llvmpipe frames drifting between runs on the same
image (then the tolerance, or the choice of imaged scenes, was wrong), or
an image comparison wanted on a real GPU in the release-candidate harness.
