# D571: The Spout sender calls the installed library's C++ ABI

Date: 2026-11-26
Status: Revised by D572
Areas: output, native, compatibility
Backlog: M-06
Related: D570, D556

## Revision

The 2.007 library Spout ships today exports none of the method names below;
it hands out an object with a vtable instead. The runtime-loading decision
here stands, the call mechanism does not: see D572.

## Context

M-06 needs Strobe to publish its picture to Spout (D570). The Spout SDK is
C++ with no C entry point, and the machine this was built on has no Spout SDK
headers or import library: what it has is `SpoutLibrary.dll`, the 2017 build
that ships with an application (Synesthesia). That DLL exports the `Spout`
class's methods with MSVC name mangling and exactly one unmangled export,
`GetSpout`, which returns the instance those methods are called on.

Adding the SDK would mean vendoring `SpoutSDK` headers and a `.lib`, which is
a build-time dependency on a Windows-only, C++-only artifact for a crate that
must keep building on Linux and macOS. A separate C++ shim crate would add a
second compiler to the build for four calls.

## Decision

The sender loads the installed `SpoutLibrary.dll` at runtime through
`libloading`, resolves the mangled exports by name, and calls them through
function pointers whose signatures were read from the DLL's exports and the
SDK's declarations:

| Call | Export | Signature |
| --- | --- | --- |
| instance | `GetSpout` | `Spout* GetSpout()` |
| create | `?CreateSender@Spout@@QAE_NPBDIIK@Z` | `bool (const char*, unsigned, unsigned, DWORD)` |
| send | `?SendTexture@Spout@@QAE_NIIII_NI@Z` | `bool (GLuint, GLenum, unsigned, unsigned, bool, GLuint)` |
| release | `?ReleaseSender@Spout@@QAEXK@Z` | `void (DWORD)` |

The vtable is not touched and no other export is called: the four calls are
the whole surface, and each is reached through a private safe function with
one `unsafe` block and its `// SAFETY:` note, which
`strobe-conventions`'s unsafe boundary names for this file.

Consequences of calling the library rather than linking it:

- No SDK, no import library, no C++ compiler, and nothing Windows-only at
  build time: the crate builds everywhere and the sender is a reasoned failure
  away from Windows and away from a machine without the DLL.
- The sender is loaded and called only on the render thread, with the GL
  context current, because `SendTexture` crosses into Direct3D through
  `wglDX*` interop; the `Spout` instance is stored as an address, never as a
  pointer that outlives its thread.
- A missing or older DLL is a `Problem` with what to install, not a crash; a
  DLL whose exports do not match is refused by name.
- The mangled names are MSVC's, so a differently built library (MinGW, a future
  ABI change) is refused rather than called wrongly. Spout has kept this
  interface since 2.004, and the SDK's own `SpoutLibrary` header declares the
  same four calls.
- Spout fixes a sender's size when it is created, so a resize closes and
  reopens the sender; the host already knows the picture's size a frame later.

## Alternatives rejected

- **Vendor the Spout SDK.** Windows-only headers and a `.lib`, plus a build
  script, for four calls; also stale the moment a user's Spout is newer.
- **A C++ shim crate.** A second toolchain in the build for the same four
  calls, and it still needs the SDK's headers.
- **`spout2` Rust bindings from crates.io.** They bind the SDK's C++ sources
  through `cxx`, which is the shim by another name.
- **A Spout input first.** Input is a media source (`spout:<name>`), which
  belongs with M-04 (D570), not here.

## What this does not settle

- A 2017 `SpoutLibrary.dll` that shipped inside another application may be
  older than the Spout 2.007 receiver interface; the sender reports what the
  library says rather than guessing, and M-06's machine check is the proof.
- Nothing here makes Spout appear on a machine without it: the Settings row and
  the console say where to get it (`spout.zeal.co`).
