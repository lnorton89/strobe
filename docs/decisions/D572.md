# D572: The Spout sender calls the 2.007 library's vtable, not mangled exports

Date: 2026-11-26
Status: Accepted
Areas: output, native, compatibility
Backlog: M-06
Related: D570, D571

## Context

D571 called `SpoutLibrary.dll`'s C++-mangled methods, because the copy on this
machine (a 2017 build inside Synesthesia) exports `?CreateSender@Spout@@…`,
`?SendTexture@Spout@@…` and `?ReleaseSender@Spout@@…` under those names.

That copy is 32-bit, so the 64-bit build never loaded it and no picture was
ever shared. The 64-bit library Spout actually ships — 2.007.018, from the
`Spout-SDK-binaries` release asset — has no such exports. It exports one
symbol, `GetSpout`, which returns a `SPOUTLIBRARY*`: a COM-like object whose
first word points at a vtable of virtual calls, the interface
`SPOUTLIBRARY/include/SpoutLibrary/SpoutLibrary.h` declares. Nothing is
exported by method name.

## Decision

The sender keeps the DLL route of D571 (found at runtime, `libloading`, no SDK
at build time) and calls through the object's vtable instead of by symbol
name:

| Call | Slot |
| --- | --- |
| `ReleaseSender(DWORD)` | 2 |
| `SendTexture(GLuint, GLuint, unsigned, unsigned, bool, GLuint)` | 4 |
| `IsInitialized()` | 6 |
| `GetName()` | 8 |
| `GetWidth()` / `GetHeight()` | 9 / 10 |
| `GetFps()` | 11 |
| `CreateSender(const char*, unsigned, unsigned, DWORD)` | 70 |

Those numbers are not taken from the header. The header's own numbering is
one slot out from the shipped binary (it lists `CreateSender` at 69 and
`GetName` at 7), so the numbers above were read from the offsets MSVC emits
for the vendor's own compiled calls (`call qword ptr [rax+…]`, with the SDK's
`.lib` linked and calls not devirtualised). A wrong slot is a wrong call, so
the compiler's answer was preferred to a reading of the header.

`CreateSender` is called with the picture's real size on the first frame, and
again on a resize, because Spout fixes a sender's size when it is created.

The sender also asks the library what it did: after creating, it reads
`IsInitialized`, `GetName`, `GetWidth` and `GetHeight` and logs those, and
after the first successful send it logs `GetFps`. A library that refuses, or
whose vtable is not this layout, produces a stated failure rather than a
silent one; the log's numbers are Spout's, not ours.

## Evidence

On the development machine, with the 64-bit 2.007.018 library beside the
executable, `strobe --scene 01-aurora-gradient --spout StrobeProbe` logged:

```
sharing the output through Spout as `StrobeProbe`
Spout reports sender `StrobeProbe` live at 960x540; a receiver can list it
Spout is carrying the picture at 75.0 fps
```

and a separate process built against the vendor's header and `.lib` listed
`senders: 1`, `[0] StrobeProbe info=1 960x540 fmt=87` — DXGI format 87 is
`B8G8R8A8_UNORM` — with a non-null shared-texture handle.

## What this does not settle

- No vtable version check: a future library that moves these slots would be
  called wrongly. The three calls used are the earliest Spout declares and
  have not moved since 2.006, and the self-check logs a failure when the
  object says nothing is live; a checksum or a `GetSDKversion` probe is the
  next step if Spout ever changes the order.
- `GetSenderList` returns `std::vector<std::string>` and is not called: C++
  containers across the boundary are exactly what this avoids.
- A sender killed hard (a task manager kill instead of a close) leaves its
  name in Spout's list until Spout reaps it; the next sender with that name is
  listed as `name_1`. `ReleaseSender` on a normal close removes it.
