# D533: CI runs xtask's lanes, strictly, and one `ci-ok` check gates master (2026-11-03, engineering audit)

**Context.** The engineering audit of 2026-10-28 found that `cargo xtask ci`
was described as running exactly what CI runs, and did not. It covered
fmt, clippy, the no-MIDI check, the tests, the cross-checks and the
generated files. It left out the Linux job's Xvfb app smoke, the
auto-controls window tests, both scene-library renders and the Windows
job's optimised builds. macOS's exclusions lived only in YAML. A missing
tool was reported as skipped, but the run still ended "CI should agree".
The master ruleset required eight jobs by name, so a job that never
started, or was renamed, left nothing for the ruleset to wait on.

**Decision.**

- **The commands live in xtask, as lanes.** `cargo xtask ci [lanes]`:
  `fmt`, `check`, `test`, `deny`, `generated`, `render`, `build`,
  `conventions`, and `all`, which is every lane but `conventions`. Each
  lane holds each host's policy in Rust. On Linux, `check` adds the
  no-MIDI and Windows cross-checks and `render` runs. On Windows, `build`
  runs. On macOS, `check` and `test` drop the crates with a GL context and
  run the whole-workspace clippy as information. Each CI job installs
  prerequisites, restores its cache and runs
  `cargo --locked xtask ci --strict <lanes>`. The workflow no longer lists
  a cargo command.
- **Missing is not the same as not here.** A lane that does not apply to a
  host is `n/a`, as CI's job for that host would treat it. A step that
  applies but whose tool is absent (cargo-deny, the Windows target,
  xvfb-run) is `MISSING`. The run then ends "partial", never "CI should
  agree". `--strict` turns that into a failure, and it also fails a run
  that changed `git status`. `cargo xtask ci doctor` lists every step's
  state and the command that installs what is missing.
- **`--locked` everywhere and timeouts in Rust.** Every cargo command
  xtask runs that resolves dependencies passes `--locked`, and a test
  asserts it. Long steps have their own timeouts, enforced by killing
  the child: the tests 45 minutes, the Xvfb steps 15, the renders 20,
  each build 40.
- **One required check.** A `ci-ok` job runs after all the others, even
  when one failed. It passes only when each job's result is what the
  `changes` job's verdict calls for: the platform jobs pass and `docs` is
  skipped, or the reverse for a docs-only pull request. Anything failed,
  cancelled or skipped out of turn fails it. The ruleset requires
  `ci-ok` alone (switched 2026-11-04, once `ci-ok` had passed on master).
- cargo-deny runs from a pinned prebuilt binary (`taiki-e/install-action`,
  cargo-deny 0.20.2), the same command as locally, rather than from the
  Docker action.

**Trade-off.** Every job now builds xtask before its first check, a
minute on a cold cache (resvg is the bulk). Each job caches the build.
A step's output now appears inside one Actions step rather than one step
each. The summary at the end, also written to the job summary, names
each step and how long it took.

**Test.** `xtask`'s unit tests plan every host's lanes without running
anything. They check that each host gets its CI job's steps, that every
resolving cargo command is `--locked`, that a missing tool is
`MISSING` and that `--strict` fails it, that a changed tree fails, and
that a hung step is killed at its timeout. `ci-ok` was checked on this
pull request's own run.

**Would reopen:** a merge queue, which needs `merge_group:` on the
workflow and `ci-ok` to run on it. Also a lane that cannot run inside
xtask, such as a service container or a matrix, which the workflow would
then own.
