# D537: the package is built and checked by xtask on every pull request, and a release candidate has a harness (2026-11-03, engineering audit)

**Context.** The release zip was staged by a bash step in `release.yml`
and zipped with 7-Zip, so CI never built the package a release would
ship. Nothing ran the exact archive except a person on the T480 (R-03,
R-04). Windows CI proved the build linked, and its 153 skipped GPU tests
proved nothing about rendering. The app's build script also let a Windows
build with no resource compiler ship a `strobe.exe` with no icon and no
version, with only a warning. The audit asked for:
- a package smoke lane that checks the archive's contents, DLL hashes,
  notices and symbols, and runs it from outside the checkout;
- a release-specific failure when the resources are missing;
- a release-candidate harness for a trusted machine, with machine-readable
  evidence;
- no unrestricted personal or venue machine attached to untrusted pull
  requests.

**Decision.**

- **`cargo xtask package`** stages and zips the package from any profile's
  build: the program, the pinned DLLs and their licence file (each hash
  checked against `scripts/native-deps.json`, D536), the scene library,
  README, LICENSE, THIRD_PARTY.md and the generated notices, and a separate
  symbols zip holding `strobe.pdb`. It uses Windows' own `tar.exe`, so it
  needs no tool beyond the OS. The release workflow runs it in place of
  its bash and 7-Zip step.
- **`cargo xtask package-check <zip> [--symbols <zip>]`** unpacks into the
  system temp folder, never the checkout, so nothing it runs can find a
  developer's file. It checks:
  - the file list, in both directions (missing files and unexpected ones);
  - every library scene is present;
  - the DLLs against the pin;
  - the notices are the generated file;
  - the version resource names the workspace version;
  - the PDB's GUID, read from the MSF information stream, equals the GUID
    in the program's CodeView record;
  - `strobe --diagnose` runs from the unpacked folder, with its files in a
    scratch folder (`STROBE_DIAG_DIR`), and reports the pinned ANGLE.

  The release runs it before the SBOM and attestation, so a bad package
  stays a draft.
- **A `package` lane** in `cargo xtask ci`, which CI's Windows job runs
  after `build`. It fetches ANGLE from the manifest (cached by the
  manifest's hash), packages the `release-fast` build and checks it, so
  every pull request proves the package. The job sets
  `STROBE_REQUIRE_RESOURCES`, as the release build does, and the app's
  build script then fails when there is no resource compiler instead of
  warning.
- **`cargo xtask rc --zip <zip> --symbols <zip>`** is the
  release-candidate harness, for the T480 or any real Windows machine, run
  by hand on the exact draft archive. It:
  - runs the package check;
  - draws scene 01 for `--frames` frames on each `--backend` (native and
    ANGLE-D3D11 by default) with both screenshots;
  - optionally runs a soak;
  - injects `STROBE_FAULT=crash@120` and symbolicates the dump against the
    symbols zip's PDB, expecting Strobe's own function names.

  It writes `evidence.json` with the archive's and the symbols' SHA-256,
  the `--diagnose` report (build, GPU, driver), each step's settings and
  result, and the checks that stay manual. It never runs on a pull
  request.

**Trade-off.** The Windows job now downloads the Electron archive when the
manifest changes, and spends about ten seconds packaging and checking.
`package-check` asks PowerShell for the version resource, rather than
this crate parsing `VS_VERSIONINFO`.

**Test.**
- On LIGHTNING: a `release-fast` build, with `STROBE_REQUIRE_RESOURCES`
  set, was packaged and passed all ten checks, including the PDB GUID
  match and `--diagnose` verifying ANGLE from the unpacked folder.
  `cargo xtask ci --strict package` passed too.
- xtask's tests: the CodeView reader on xtask's own binary, a file that is
  neither a PE nor a PDB refused, and the manifest naming the licence file.
- The harness's first real run is the next release candidate on the T480
  (backlog R-03).

**Would reopen:** an installer (MSI, MSIX) replacing the zip. The checks
would then run against the installed folder. Or a self-hosted runner with
a GPU, isolated from pull requests, which could run the harness on a
schedule.
