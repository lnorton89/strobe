# D575: Spout and NDI input are live media sources, `spout:<name>` and `ndi:<name>`, on the webcam's capture path

Date: 2026-11-26
Status: Accepted
Areas: output, capture, gfx, scene, app, native
Backlog: M-07
Related: D528, D570, D572, D573, D574, D238

## Context

Issue lnorton89/strobe#116 asks for input as well as output, so that other
apps' feeds can be used inside scenes. The M-06 research page placed input
in the M-04 media family, not in M-06: a receiver is a media source, the
mirror of the webcam (D528), and shares nothing with a sender beyond the
library. SSF has no `syn_MediaType` value of its own for a shared texture
(Q22).

The webcam path already has what a live source needs: a capture thread per
source with a watchdog and reconnect by name (`strobe-capture`'s
supervisor), a one-picture mailbox into one reused texture
(`strobe_gfx::live`), a failure said once that reads black, and a registry
that shares one capture between players.

## Decision

1. **A Spout sender is the media choice `spout:<name>`, an NDI source
   `ndi:<name>`**, beside `camera:<name>`. `strobe_scene::live` names all
   three kinds (`Kind`, `Source`, `source_of`, `path_for`, `resolve`); a
   live path is never joined to a folder, and a scene's own `MEDIA` cannot
   name one. Every store of a media choice (`--media`, the Inspector, a
   cue, a preset) takes them unchanged, with D217's precedence.
2. **One hook for every kind.** `strobe_gfx::live::LiveSources::open`
   takes a `Source` (kind and name), replacing `camera(name)`. The player
   is unchanged otherwise: at most one upload a frame into one reused
   texture with the slot's `WRAP`/`FILTER`, no allocation and no driver
   query unless the size changes, and `syn_MediaType` 3 while it shows
   (Q22 gives no other value).
3. **The webcam's supervisor runs them.** Spout and NDI are two more
   `strobe_capture::Backend`s (`strobe_app::share_input`), over receivers
   in `strobe-output` (`SpoutReceiver`, `NdiReceiver`, `NdiFinder`). So the
   watchdog, reconnect by name, once-per-outage failure and retirement when
   unshown are the camera's, already tested. `strobe-capture` gains RGBA
   and BGRA (four bytes, top row first) and `Sink::kind`, so its log lines
   and failures name the kind ("Spout sender", "NDI source").
4. **Spout reads on the capture thread, not the render thread.** The
   receiver calls `CreateOpenGL` for Spout's own hidden context on that
   thread and reads with `ReceiveImage` into the stream's reused buffer,
   RGBA top row first. Each read first connects with `ReceiveTexture` and
   no texture, which copies nothing but refreshes the sender's size, so the
   buffer is that size before Spout writes into it. The receiver's vtable
   slots (16, 18 to 26, 58, 59, 98, 99) are the ones `cl` emits for calls
   through the 2.007.018 header, read from a listing of a probe as D573
   read the sender's; `spout_receive.rs` joins `spout.rs` on the unsafe
   allowlist under the same leaf rules.
5. **NDI asks for RGBX/RGBA**, so NDI decodes and only the rows turn over;
   BGRA from a source with alpha is accepted too, anything else is refused
   by name. One finder is made per process and keeps discovering; the
   first listing waits up to 2 s for its first answers.
6. **Pacing and idle senders.** A Spout stream polls every 4 ms and hands
   over at most one picture per 8 ms (a sender that does not count frames
   is not read flat out). A sender that is still there but sends nothing
   new keeps its last picture: the stream hands it over again every second,
   so the watchdog never mistakes an idle sender for a stopped one. No
   first picture within 3 s is a stalled source; a sender that closes, or
   an NDI source that disconnects, fails at once.
7. **Failure wording per kind.** Black and type 0, said once per outage,
   with an action written for Spout or NDI (`strobe_app::live::action`):
   not running, closed, stopped sending, unreadable, no library or runtime.
   The library and runtime missing are `Cause::Unsupported`; a missing NDI
   runtime names NDI Tools, as the sender does (D573), and is not retried
   until the next run.
8. **UI and CLI.** The Inspector's Media row gains Spout and NDI beside
   Camera, each listing on its own thread with one button per source.
   `strobe --list-spout` and `--list-ndi` print the paths `--media` takes.

Not taken now:

- **Zero-copy Spout input**: `ReceiveTexture` into the player's texture on
  the render thread. It saves a readback and an upload per frame, but puts
  Spout's GL state changes and its sender lookup inside the frame, and the
  player would need a GPU-side source beside the mailbox. The measured
  cost of the readback on the T480 decides it.
- NDI audio, NDI's low-bandwidth preview stream, and an NDI source's alpha
  (nothing would composite it until D248).
- The Media Overlay, which shows a live source in scenes that do not read
  `syn_Media` (C-01, as for the webcam).

## Consequences

- Spout and NDI input cost what a camera costs: a CPU copy per frame on the
  capture thread, and one upload on the render thread. A 720p feed is
  3.7 MB a frame each way.
- Verified on LIGHTNING (Windows 10, RX 580), 2026-11-26, with Strobe
  sending a known gradient through `--spout StrobeCheck --share-size
  640x360` and a second instance receiving it with `--media
  spout:StrobeCheck`:
  - `--list-spout` lists the sender, as does the independent probe.
  - The received picture is upright and exact: the top-left marker reads
    (255, 255, 191), the corners match the sender's gradient, and blue 191
    is `syn_MediaType` 3.
  - Killing the sender: one warning and one asset record ("closed", with
    the Spout action), and the output reads black with type 0.
  - Starting the receiver first: "not running" said once, then the picture
    arrives by itself 5.5 s later, when the sender starts.
- NDI input verified on LIGHTNING the same day, once NDI 6 Tools 6.4 was
  installed (the runtime is found through `NDI_RUNTIME_DIR_V6`, which a
  shell started before the install does not have):
  - `--list-ndi` lists `LIGHTNING (StrobeNdiCheck)`, sent by Strobe with
    `--ndi StrobeNdiCheck`.
  - The received picture is upright and exact within two levels after
    NDI's 4:2:2 round trip: the marker reads (255, 255, 191), the corners
    (2, 2, 191), (254, 1, 191) and (254, 252, 191). The source opened 2 s
    after it was chosen, with no false "not found" while discovery
    answered.
  - Killing the sender: "closed" said once, and black. NDI keeps listing a
    stopped source for a while, so the stream reopens and starves every
    few seconds meanwhile, quietly.
- Tests: `strobe_scene::live` (round trips, NDI's `MACHINE (Name)`, never
  joined); `strobe_capture::convert` (RGBA and BGRA turned over, alpha
  kept); `strobe-gfx/tests/live.rs` (a Spout and an NDI source upright as
  type 3 by their own kind, black and said once when lost);
  `strobe_app::live` (one mailbox per kind and name, retired when unshown,
  a missing sender said once in its own words against the real library and
  runtime state of the machine, every action worded for its kind);
  `strobe_app::share_input` (the pacing policy: new pictures at once, an
  idle sender held, a resized buffer not shown as the old picture, no
  first picture starved, the gap); `strobe-output` (listing answers with or
  without Spout; a finder starts or names NDI Tools).
- **Not verified:** a third-party sender (Resolume, TouchDesigner, OBS) as
  the source; the Media row's buttons clicked on screen; the copy's cost on
  the T480.

**Would reopen:** the T480 finding the readback and upload too costly (then
zero-copy `ReceiveTexture`); a sender whose `IsFrameNew` misbehaves (then
pace by `GetSenderFps`); SSF documenting a media type for shared textures.
