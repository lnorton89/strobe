# D535: the audio tests are optimised, Windows tests run through nextest, and build speed is measured before it is bought (2026-11-03, engineering audit)

**Context.** The audit sampled three CI runs. Windows was the longest job,
and its test step took about 245 s, compilation included. Within that,
the audio crate's 90 tests ran for 62 s. They synthesise and analyse long
stretches of signal in unoptimised DSP code. The workspace already
optimises its dependencies in debug builds (D487), but not its own
crates. The audit asked for measurement before more infrastructure: a
targeted optimisation first, then a nextest pilot, `--timings` reports,
and sccache and thin LTO only as measured trials.

**Decision.**

- **`[profile.test.package.strobe-audio] opt-level = 2`**, in the test
  profile only, so a debug app build keeps the crate debuggable. Overflow
  checks and debug assertions stay on, and the signal durations are
  unchanged, because the tempo and downbeat tests need them. Measured on
  the owner's desktop (LIGHTNING), with the crate's tests rebuilt from
  clean each time:

  | | build | run | total |
  |---|---:|---:|---:|
  | opt-level 0 (before) | 9.6 s | 31.6 s | 41.2 s |
  | opt-level 2 | 27.4 s | 1.8 s | 29.2 s |

  The run is 17 times faster. On CI the 62 s run should shrink to a few
  seconds, and the rebuild only happens when the crate changes.
- **nextest on Windows, as a pilot.** `cargo xtask ci test --nextest` runs
  the tests through cargo-nextest and the doctests through
  `cargo test --doc`, which nextest does not run. Each test gets its own
  process, a time, a five-minute limit and a JUnit record, and the test
  binaries are scheduled together. Only the Windows job uses it, with
  cargo-nextest 0.9.151 pinned. Linux and macOS keep `cargo test`, so
  the two runners can be compared on the same commits before either is
  adopted everywhere. Settings are in `.config/nextest.toml`.
- **Timings are kept.** The `build` lane passes `--timings`. The Windows
  job uploads `target/cargo-timings/` and nextest's `junit.xml` as
  `windows-timings`, kept 30 days.
- **sccache and thin LTO are experiments, not settings.** The new
  `Experiments` workflow runs the Windows `check` and `test` lanes through
  sccache, backed by GitHub's cache and without rust-cache, every Monday
  and on demand, and puts the hit rate in its summary. When started by
  hand with `lto`, it also builds the shipping profile and a new
  `release-thin` profile, and reports build time and binary size. A
  thin-LTO switch still needs the T480's frame times (D504). Local
  `release-fast` keeps incremental builds, which sccache cannot cache.

**Trade-off.** One more profile (`release-thin`) exists only to be
measured. The nextest pilot makes the Windows job's test step look
different from the other two jobs' until a decision is made, and the
JUnit and timings artefacts are the data that decision needs.

**Test.** The before and after numbers above. `xtask`'s planner tests
cover `--nextest`: nextest with the CI profile on a runner, doctests
through cargo, and nextest missing when asked for. On LIGHTNING, nextest
ran the whole workspace, 2,199 tests, all passing, in 28 s after the
build. So no test depends on sharing a process with another.

**Would reopen:** nextest's per-process start-up costing more on Windows
than its scheduling saves (the JUnit times will say), or sccache showing
a hit rate high enough to pay for its transfer, in which case it moves
into ci.yml's Windows job in place of part of rust-cache.
