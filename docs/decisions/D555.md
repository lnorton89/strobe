# D555: a hand-loaded scene compiles in the background where the driver can, and the output plays on meanwhile (2026-11-05, backlog G-08)

**Context.** ANGLE-D3D11 links heavy scenes far slower than native GL. On
the T480's UHD 620, `12-silicon-atlas` took 5.45 s against 0.42 s (Task
47). On LIGHTNING's RX 580 it took 2.7 s against 66 ms. A scene loaded by
hand compiled on the thread that draws the output, so the output froze
for the whole compile. The v0.3.0 release, loading `12-silicon-atlas` on
ANGLE-D3D11 on LIGHTNING, froze it for 1,744 ms. ANGLE is the fallback
for a broken WGL driver, and the machine on it is the one that can least
afford a freeze. D542 already named the way out:
`GL_KHR_parallel_shader_compile`.

**Decision.**

- **Detected once, and turned on.** A `Gl` notes when the context offers
  `KHR_` or `ARB_parallel_shader_compile`, and then asks for as many
  compiler threads as the driver will give. `Caps::info.parallel_compile`
  reports it; the bench prints it. On LIGHTNING, native AMD and
  ANGLE-D3D11 offer it and ANGLE-Vulkan does not (it compiles this scene
  in 12 ms anyway). The browser sandbox keeps the blocking path, since
  WebGL needs the extension enabled first.
- **A player is built in two steps.** `ScenePlayer::begin` hands every
  pass's shader to the driver and returns without waiting. All passes
  are started before any is read, so the driver builds them side by side.
  `PendingPlayer::ready` polls `COMPLETION_STATUS_KHR`.
  `PendingPlayer::finish` reads how each program went (a broken pass is
  still named at its own `file:line`), resolves locations and allocates.
  `with_extras` is `begin` then `finish`, so every other caller is
  unchanged. `Session::begin`, `PendingSession::finish` and
  `Session::load` are the same split one level up.
- **A hand load uses it.** A load the UI asks for (a click, the palette,
  OSC, MIDI, the remote) begins, and the scene before it plays on.
  "Preparing" stays up. Each control-window frame polls, and the scene
  swaps in when the driver is done. A new request replaces it. A
  playlist start, a context rebuild or quitting drops it. The prerender
  and thumbnail jobs wait for it. A parked scene still plays at once. A
  driver without background compiles loads as before.
- **The poll is not a counted driver query.** Like a fence's
  zero-timeout wait, it is how a frame avoids waiting, and it runs only
  while a scene is loading. `strobe_conventions::driver_queries` exempts
  `program_completion`, with that reason. A scene that only plays still
  asks the driver nothing (D497).
- **The fallback order is not changed.** ANGLE-Vulkan compiles fast, but
  D485's order stays. The load path, not the backend, was what froze the
  output.

**Trade-off.**
- A scene loaded by hand appears when the driver is done, not on the
  frame after the click. That is as long as before, but nothing stops
  meanwhile.
- The first draw of a freshly linked program can still take driver time:
  one cold run on LIGHTNING had a 452 ms gap at the swap, against 36 ms
  warm.
- Playlist precompile (D151) and the launch prerender (D542, D550) still
  compile one step at a time on the frame thread, now with every pass of
  a step built side by side. Moving them onto the same poll is the next
  step.

**Test.**
- `render.rs`'s `a_build_begun_polled_and_finished_draws_what_a_plain_build_draws`,
  in both dialects: a begun, polled and finished two-pass build draws
  what a plain build draws, and a broken pass is still named at
  `main.glsl:4`.
- `strobe-bench` now times `blocked` beside `compile`. On LIGHTNING's
  ANGLE-D3D11, `12-silicon-atlas` compiled in 1,931 ms and blocked
  6.9 ms (2,665 ms before, compiled one pass after another).
- On LIGHTNING with ANGLE-D3D11, a hand load of `12-silicon-atlas` over
  OSC:

  | | handed over | ready | minute's worst gap |
  |---|---:|---:|---:|
  | v0.3.0 | (blocking) | 1,740 ms | 1,744 ms |
  | this, cold | 11 ms | 3,572 ms | 452 ms |
  | this, warm | 2 ms | 2,142 ms | 36 ms, 0 missed refreshes |

- The T480's numbers go in `hardware/T480.md`.

**Would reopen:**
- a driver whose `COMPLETION_STATUS` poll is itself slow;
- the first-draw cost becoming the stall that matters, which priming in
  the background could take;
- moving the playlist precompile and the prerender onto the same poll.
