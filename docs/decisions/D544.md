# D544: what the audit work had skipped: a static C runtime, the imports and the loaded ANGLE checked, the browser engine built, generators that reach the code, and a changelog that can be corrected (2026-11-03, owner's request)

**Context.** Asked what had been left undone, the answer was a list of
items that were narrowed, skipped or never run during D533-D541. The
owner asked for all of them. Doing them found one real shipping problem.

**Decision.**

- **The MSVC C runtime is linked statically** (`+crt-static` for
  `x86_64-pc-windows-msvc`, in `.cargo/config.toml`). The new import check
  below found `strobe.exe` importing `VCRUNTIME140.dll`. That DLL is not
  part of Windows and was not in the zip, so a clean machine without the
  Visual C++ redistributable would refuse to start Strobe. The machines it
  had been tested on all had the redistributable installed. The C
  dependencies (QuickJS, ring) follow through the `cc` crate, which
  compiles them `/MT`.
- **`package-check` reads the import table.** Every DLL `strobe.exe`
  imports directly must be part of Windows (the API sets and a named list
  of system libraries) or be in the package.
- **`--diagnose` names the ANGLE that loads**, not only the files beside
  the program. It opens one hidden ANGLE-only window and reports its
  `GL_VERSION`, which carries ANGLE's own build (`ANGLE 2.1.25847 git
  hash: …` on LIGHTNING). A DLL elsewhere on the search path could
  otherwise win while the files beside the program still matched the pin.
- **The ANGLE build script also watches `fetch-angle.ps1`**, and
  `STROBE_REQUIRE_ANGLE` makes a failed fetch fail the build. A dev build
  still only warns, as D498 chose; the owner kept that.
- **The browser engine is built in CI.** The Linux `check` lane clippies
  `strobe-web` for `wasm32-unknown-unknown`. That is the one intended
  configuration of strobe-gfx without `native`, and of strobe-audio
  without `capture`.
- **Property generators that reach the code** (D539). The first
  generators were mostly refused at the door:
  - a playlist generator that was not TOML;
  - scene controls written in shapes no scene uses;
  - client messages outside the server's own limits.

  Each now builds valid input up to the grammar's limits, and a guard
  fails the test when too few generated cases parse. New properties:
  - the timeline planned from any playlist, at any tempo from 0.001 to a
    million BPM;
  - the WebSocket frame reader on any bytes;
  - out-of-range desktop input always refused;
  - any Shadertoy title and id giving one safe folder name;
  - the whole-shader rewriters (hoisting, uniform initializers,
    promotion).
- **Two more corpus fixtures**: an `IMAGES` scene and an `#include` scene
  (D534). `cargo xtask corpus --profile` builds the harness in any
  profile. The owner kept the render lane's dev profile.
- **`CHANGELOG.corrections`**: a subject found wrong after it was pushed is
  corrected by full hash, not by rewording the commit, which would rewrite
  every hash after it. Its first entry moves #63's subject from D516 to
  D521.
- **PSScriptAnalyzer is fetched, not installed.** `Install-Module` took
  108 s of every Windows job, more than clippy, mostly bootstrapping NuGet.
  The job now downloads the pinned 1.25.0 package from the gallery, checks
  its SHA-256 and expands it into PowerShell 5.1's per-user module folder,
  in about 2 s.
- **Coverage was read for recovery and protocol cases** (D539), with
  `cargo llvm-cov` 0.9.1 over strobe-remote, strobe-io and strobe-audio
  (lines 92.4% overall). The protocol gaps are now tests:
  - an upgrade without its tokens, with a bad key or by POST, a head past
    8 KiB, an HTTP/1.0 request, and the web app's files under GET only;
  - a proof with no challenge, and full desktop access switched off or
    Revoke all pressed between a challenge and its proof;
  - the desktop client refusing a wrong accept key, a non-101, a hang-up
    and a public or port-0 address, answering a ping, and ending on a close
    or an unknown message.

  That moved `client.rs` from 77% to 88% and `server/session.rs` from 86%
  to 91%. What stays uncovered needs a device: the capture worker's
  reopen loop (67%; its backoff and watchdog are unit-tested, the loop is
  R-01's unplug test), `capture/device.rs`, and the MIDI ports (P-04).
- **The macOS informational clippy was read, not trusted.** Its raw
  outcome is a failure: strobe-gfx's EGL code does not compile on Apple
  targets (the CGL port), as the job's comment says. The job shows success
  only because the step is allowed to fail.
- **Evidence gathered off this machine:**
  - The T480 build timings are in BENCHMARKS.md (2026-11-03).
  - A release dry run on the mirror built the fat-LTO package with
    `--target` and passed `package-check`. It also found an unquoted
    `$(find …)` in `release.yml`'s upload (fixed in D541's pull request).

**Not done here, and why:**
- **The release-candidate harness on the T480.** The laptop's session
  rightly would not install the symbol tools or run a downloaded build on
  another session's request. It waits for the owner to approve it there.
- **The thin-LTO frame-time bench, and the nextest and sccache
  decisions.** These need data that does not exist yet (backlog D-07).

**The release path, end to end.** A second dry run on the mirror ran the
whole of `release.yml` from this branch, version 0.2.1, and passed (run
41792295320):
- the tag resolved to one commit;
- all of `ci.yml` passed on that commit;
- the fat-LTO build passed `package --target` and `package-check`;
- the release was published.

`gh attestation verify` accepts the archive. Its provenance names
`refs/tags/v0.2.1` at `a5d085d`, the tagged commit, which settles the
audit's question about which commit the provenance names. The SBOM
attestation verifies too, and the SBOM's 297 components include the four
native DLLs with their pinned hashes (D536). The first try failed only
because the dry run put the version bump and the changelog section in one
commit. CONTRIBUTING's order is two commits, and that order passed.

**Test.**
- `package-check` on a `release-fast` package: before the change it named
  `VCRUNTIME140.dll`; after it, it passes.
- `--diagnose` on LIGHTNING printed the loaded ANGLE.
- Every property passes with its parse guard.
- The corrections parser has a unit test.
- The fixtures' baselines come from CI's first run, as before (D534).

**Would reopen:** a dependency that cannot be built with a static C
runtime, which would mean shipping `vcruntime140.dll` in the package
instead.
