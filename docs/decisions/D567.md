# D567: a desktop controller can watch the host's frame timing live, one sample a second, without the picture stream (2026-11-25, backlog L-10, on the owner's go-ahead)

**Context.** A show's performance was visible from another computer two ways.
One was the `perf:` line the host logs once a minute (D206), read over a share
or SSH after the fact. The other was the Diagnostics pane seen through a
desktop controller (D275), which needs the host to stream JPEG captures of its
control window at up to 5 Hz. That raises the control window's redraws from
about 120 a minute to about 300, so watching that way changes the numbers you
are watching (D290). Nothing carried the numbers themselves over the network.

**Decision.**

- **The same counting over one second.** `stats::PerfWindow::take_after`
  returns a `PerfSummary`. The minute's `perf:` line and the live sample are
  both made from it, so the two count alike: frames, late frames, missed
  refreshes (D316), worst gap, mean GPU time, render scale, and the control
  window's redraws with their make-current, layout, paint and swap means. The
  sample also carries the smoothed CPU time, the frame budget, whether
  adaptive resolution is on, whether the control window is slowed (D216), and
  whether the fullscreen output has lost the focus (D453).
- **Published into one slot.** The app takes a summary once a second and hands
  it to `bridge::AppEnd::publish_perf`, which replaces the previous sample under
  a new revision. Nothing queues. Each frame adds a few numbers to a second
  window beside the minute's, and the sample is built once a second, not per
  frame. A float that is not finite is stored as 0, because JSON cannot carry
  it and a failed write would drop the connection.
- **Opt in, the way D513 works.** The controller sends `perf_open`, and only
  then does the host send `perf` messages on that connection, at most one per
  revision. An older controller closes the connection on a message type it
  does not know, so nothing is sent unasked. An older host answers
  `invalid_request`. The controller sends `perf_open` before
  `desktop_controls_open`, so the first such answer belongs to the feed, and
  carries on without it. `perf_close` stops the feed.
- **Desktop controllers only, and no lease needed.** A pairing for desktop
  control, approved or proved with the venue trust file (D288), may watch. A
  phone's pairing is limited to show commands and is refused `unauthorized`.
  Watching never takes the input lease or asks for the picture, so a watcher
  costs the host one message of about 400 bytes a second.
- **A sample tolerates fields it does not know.** Client messages refuse
  unknown fields (D236). `PerfSample` is data the host sends, so a later host
  can add a number without breaking this controller.
- **Two ways to see it.** The desktop viewer draws a strip under its toolbar:
  one line in the words of the log's `perf:` line, and a one-minute trend of
  the frame rate against the refresh rate. It turns the warning colour when a
  frame was late or missed, or the control window is slowed, or the output is
  not in the foreground. `strobe --watch-perf HOST:PORT --remote-trust FILE`
  opens no window. It proves the file, asks for the feed and nothing else, and
  prints a line a second. `--perf-csv FILE` appends a row per sample, with the
  header when the file is empty, flushed every second. `--perf-seconds N`
  stops it. A dropped connection is retried on the venue laptop's schedule
  (1 s to 15 s), and a refusal ends the watch with the reason. A watch that
  received no sample exits with failure, so a script cannot take an empty
  soak for a pass. A printed line that goes nowhere does not stop the CSV.
- **Old numbers say so.** A host whose frame loop stalls makes no samples,
  while its network thread keeps the connection up. After 3 s with no new
  sample, the strip turns the warning colour and says how long it has been.
  A new session restarts the trend, so a restarted host's run is not joined
  to the last one.
- **Only "not understood" means an older host.** A controller treats an
  `invalid_request` as "no feed here" only when its message is
  `strobe_remote::NOT_UNDERSTOOD`, the text every host sends for a message it
  cannot decode, so an unrelated refusal in the first second is not mistaken
  for one.

**Test.**
- strobe-remote: the protocol's frozen messages (`perf_open`, `perf_close`,
  `perf`) read and write byte for byte, and extra fields on the client
  messages are refused. The bridge keeps only the newest sample. Over real
  sockets, a phone is refused, a desktop controller that has not asked gets no
  sample, one that asks gets samples with a rising revision and no lease, and
  none come after `perf_close`.
- strobe-app: a one-second window and a minute's window fed the same frames
  agree. The viewer's strip receives a host's sample and asks for a redraw.
  `--watch-perf` proves a trust file, prints samples and writes whole CSV
  rows. A wrong trust file ends the watch with the reason, and an unwritable
  CSV file is reported before connecting.
- Not yet measured: a soak on the T480 comparing its `perf:` lines with a
  watcher connected and without one.

**Would reopen:** a phone page that wants the numbers (it would need its own
permission), per-pass GPU timing in the sample, or a measured cost of
watching that shows in the host's own `perf:` line.
