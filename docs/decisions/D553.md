# D553: Shadertoy cube-map inputs become scene cube maps, the keyboard is 256x3 with every key up, and the Needs-work bin is closed (2026-11-05)

**Context.** Backlog I-06. The converter refused `cubemap` inputs, bound
`keyboard` to the 1x1 black image, and PLAN.md's Needs-work bin (a folder
of failed imports with their logs) was never built. The renderer has
loaded cube maps since D185, so a cube-map input needed only the
converter and the faces' names and orientation. A 1x1 texture under a
shader that reads `texelFetch(iChannel1, ivec2(32, 0), 0)` is read out of
range, which GL leaves undefined.

**What was verified, and how.** shadertoy.com answers scripts with a
Cloudflare 403 (Q19), so its own player code was read from copies people
ship with exported shaders: `effect.js` and `piLibs.js` as vendored in
github.com/samuelmaddock/shadertoy-extension (`public/`), checked against
the later port in github.com/liriliri/luna (`src/shader-toy-player/Effect.ts`).
The two agree on everything below.

- **Face names.** `NewTexture` loads six pictures for a `cubemap` input:
  `mSrc` itself, then `mSrc` with `_1` to `_5` put before its last `.`
  (`x.jpg`, `x_1.jpg` ... `x_5.jpg`).
- **Face order and orientation.** `CreateTextureFromImage` uploads picture
  `i` to `TEXTURE_CUBE_MAP_POSITIVE_X + i`: +X, -X, +Y, -Y, +Z, -Z, GL's
  order, the order of `CUBEMAPS` `PATHS` (D185). It sets
  `UNPACK_FLIP_Y_WEBGL` to the sampler's `vflip`. Unflipped, a picture's
  top row is the face's row 0, which is what Strobe uploads for a face
  "used as decoded" (D185). With `vflip` on, every face goes up upside
  down and pictures 2 and 3 trade places (+Y gets picture 3, -Y picture 2).
  `Sampler2Renderer` reads `vflip` as on only when it is the string
  `"true"`, so it is off when absent.
- **Sampling.** Filter is the sampler's (`mipmap` builds mips); wrap is
  not set on a cube texture, and WebGL 2 cube maps are seamless.
- **Cube A.** A `cubemap` input with id `4dX3Rr` reads the shader's own
  cube-map pass (`assetID_to_cubemapBuferID`), not a picture.
- **Keyboard.** `Effect` creates one 256x3 `R8` texture, nearest and
  clamped, unflipped. `SetKeyDown(k)` sets row 0 (held) and row 1 (pressed
  this frame) at column `k`, the DOM `keyCode`, to 255 and inverts row 2
  (toggle); key up clears rows 0 and 1; after each frame row 1 is cleared.

Where a face shows on screen then follows from GL's cube-face rule (the
major-axis table), which WebGL shares: row 0 of a side face is towards +Y,
of +Y towards -Z, and of -Y towards +Z. The render test checks Strobe
against that rule, not against a picture of Shadertoy, which could not be
fetched.

**Decision.**

- **A `cubemap` input is a scene cube map.** The converter names the six
  faces as Shadertoy does, treats each as a texture asset (fetched,
  cached, pending, `--strict` and the asset folder all work as for a
  texture, D95, D417), writes a `CUBEMAPS` entry `st_cube<n>` with the six
  paths in that order, and `#define`s `iChannelN` to it. A sampler with
  `vflip` writes `"VFLIP": true` on the entry, a new `CUBEMAPS` key
  (`strobe-scene`'s `CubemapDef::vflip`) that
  `strobe_gfx::assets::load_cubemap` honours on the CPU (turn each face
  over, swap +Y and -Y), so the renderer gains no GL call. With any face
  missing the channel reads `st_black_cube`, six of the 1x1 black picture,
  which loads cleanly instead of reporting an asset problem (D185); the
  missing faces are pending and warned, as a texture is. A filter other
  than `mipmap` is a warning: Strobe's cube maps are always mipmapped and
  linear (D185), which is Shadertoy's default for one.
- **The keyboard is Shadertoy's texture with every key up.** A `keyboard`
  input reads `images/st_keyboard.png`, a 256x3 grey picture of zeros,
  nearest, clamped, unflipped. `texelFetch` at a key code is in range and
  `iChannelResolution` is 256x3, so a keyboard-reading shader runs as it
  does on Shadertoy with no key touched. The import still warns that no
  key arrives. **Key state comes from nowhere, on purpose.** The control
  window's keys are the operator's commands (cues, blackout, the
  palette), and the output window is on a projector without focus; a
  scene that reacted to them would turn a show command into a picture
  change. Interaction in Strobe is controls, which OSC and MIDI already
  map (D173); a shader author who wants a key-driven mode gets a
  control. A live feed would need a per-frame texture in the player and
  routing in the app for a feature no venue has asked for.
- **Refused, with reasons.**
  - `cubemap` **passes** (and a `cubemap` input reading Cube A): a
    cube-map buffer renders `mainCubemap` into six 1024x1024 faces a
    frame. Strobe's passes draw 2D targets; rendering into cube faces
    needs new GL leaves (a framebuffer per face) and costs six full
    passes a frame on an HD 4000. Refused until a real shader worth
    showing needs one.
  - `volume` inputs: the renderer has no 3D textures, and Shadertoy's
    volumes are its own binary files (noise and a few scans), which would
    need a decoder and new GL leaves for little-used noise. Refused.
  - `sound` passes: `mainSound` synthesises audio. Strobe listens to the
    room and draws; it plays no audio. Refused by design.
- **The Needs-work bin is closed.** A shader that cannot be converted is
  refused before anything is written, with a message naming the pass and
  channel (I-04), and the person still has the JSON they sent. One that
  converts but fails to compile is a scene in the library, and it is
  already listed under the library's "Needs work" filter and in the
  Diagnostics pane's Needs work card with its reason and Open in Editor
  (D136, D483). A separate folder of failed imports would be a
  second list of the same failures, holding files that a fixed importer
  would regenerate from the same JSON.

**Trade-off.** A cube's sampler filter is not honoured (rarely set), and a
cube map imported before its faces download reads black until it is
imported again, as a texture does. No key ever reaches a scene. The
orientation is checked against GL's rule and Shadertoy's code, not
against a frame captured on shadertoy.com.

**Test.**
- `strobe-shadertoy` `convert` tests:
  `a_cube_map_with_its_six_faces_becomes_a_scene_cube_map`,
  `a_cube_map_missing_a_face_reads_a_black_cube_and_lists_every_missing_face`,
  `a_keyboard_input_reads_a_256_by_3_image_with_every_key_up`, and the
  refusals in `unsupported_things_are_errors_that_name_the_pass_and_channel`;
  unit tests `cube_faces_are_named_as_shadertoy_names_them` and
  `the_keyboard_png_is_256_by_3_grey`.
- `strobe-shadertoy` `render` tests, headless in both dialects:
  `a_cube_map_input_shows_each_picture_where_shadertoy_puts_it` (twelve
  directions, a picture's top and bottom half on each face, with `vflip`
  off and on), `a_cube_map_with_no_faces_reads_black_and_still_renders`,
  `a_keyboard_input_is_256_by_3_with_every_key_up`.
- `strobe-gfx` `assets` test
  `vflip_turns_each_face_over_and_swaps_up_and_down_as_shadertoy_does`.
- Two new original fixtures, `cube_map.json` and `keyboard.json`, pass
  `strobe-app`'s `shadertoy_fixtures_convert_and_pass_the_harness_in_both_dialects`.

**Would reopen:** a real shader worth showing that needs a cube-map pass or
a volume; a venue that wants a scene played from keys (then a narrow
`strobe_ShadertoyKeyboard` sampler fed from OSC/MIDI-mapped keys, not the
control window); a frame captured on shadertoy.com that disagrees with
the render test; or a person losing a shader they could not send again,
which is what a Needs-work bin would have kept.
