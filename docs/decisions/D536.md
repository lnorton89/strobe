# D536: one manifest pins the native DLLs; the SBOM, the build and `--diagnose` read it; scheduled checks watch what pushes cannot (2026-11-03, engineering audit)

**Context.** The ANGLE DLLs, the D3D compiler and the Vulkan loader come
from an Electron release, pinned by version and SHA-256 inside
`scripts/fetch-angle.ps1`. Several things depended on that pin, and the
audit found gaps:

- strobe-gfx's build script (D498) took four files with the right names as
  current, so a bumped pin left every existing profile on the old DLLs
  until someone ran the script by hand.
- The release SBOM was generated from Cargo metadata, so it described
  `strobe.exe` and not the four DLLs in the same zip.
- `--diagnose` could not say which ANGLE was beside the program.
- Dependabot watches crates and actions, not an Electron archive, and
  nothing re-checked advisories between pushes.
- The flake built with nixpkgs' Rust rather than the repository's pin, and
  no workflow built it.

**Decision.**

- **`scripts/native-deps.json`** is the one machine-readable pin: version,
  source URL, the archive's SHA-256, and each file's name, SHA-256,
  component name, supplier and licence. The fetch script reads it.
- **A stamp makes a stale DLL visible.** The fetch script writes
  `angle.stamp`, holding the version, beside the DLLs it places. The build
  script watches the manifest (by a relative path, D464). It fetches again
  when a DLL is missing or the stamp names a different version than the
  manifest. A bump is one commit, and each profile refreshes on its next
  build.
- **`strobe --diagnose`** hashes the DLLs beside the program against the
  pin, which is compiled in. It reports one of:
  - the pinned version, verified;
  - not present, so native GL only;
  - which file is not the pinned one, and which are missing.
- **`cargo xtask sbom-native`** adds one CycloneDX component per DLL, with
  name, version, supplier, licence, the shipped file's own SHA-256, and the
  download URL. It refuses a file that is not the pinned one. The release
  workflow runs it on the SBOM before the SBOM is attested. A
  `LicenseRef-` licence goes in `name`, an SPDX one in `id`.
- **A Scheduled workflow** runs every Monday and on demand:
  - cargo-deny, for advisories published since the last push;
  - the pinned archive, downloaded and checked against the pin, with any
    newer release in the same major line named as a notice (a bump stays a
    deliberate commit);
  - the Nix flake, which is also checked on any pull request that touches
    the flake, the toolchain pin or the native pin.
- **Nix uses the toolchain pin.** The flake takes rust-overlay
  (`rust-bin.fromRustupToolchainFile ./rust-toolchain.toml`) for the dev
  shell and for the package's `makeRustPlatform`. The Nix job:
  - fails if `nix flake lock` would change `flake.lock`, and uploads the
    updated lock;
  - checks that the dev shell's `rustc` is the pinned version;
  - runs `nix flake check` and `nix build`.

**Trade-off.** Nix now downloads the pinned toolchain from rust-overlay
instead of using nixpkgs' cached rustc. A first `nix develop` is slower,
in exchange for one compiler everywhere. The manifest is JSON, not TOML,
because PowerShell 5.1 reads JSON natively. The build script scans it for
the version instead of parsing it, to stay free of dependencies.

**Test.**
- `xtask`'s tests: each pinned file becomes a component with its own hash
  and the right licence field, a file that is not the pinned one fails,
  and the real manifest pins four full hashes.
- strobe-app's test: a DLL with the right name and the wrong bytes is
  named in `--diagnose`.
- On LIGHTNING: the fetch script, reading the manifest, placed the DLLs
  and the stamp, and `sbom-native` added four verified components for
  them.
- The Nix job's first run on this pull request writes the new lock.

**Would reopen:** a second native dependency with its own fetch, which
would make the manifest a list rather than one `angle` entry, or the
release moving to an installer that carries its own manifest.
