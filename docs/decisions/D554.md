# D554: the sandbox's scene is its files: pictures added, includes resolved, the picture read back, presets as files (2026-11-05, backlog W-01)

**Context.** The `/play` sandbox (D524) runs the app's own player, but a
scene there was only its text.

- `IMAGES` read black.
- `#include` was left for the driver to reject.
- `textureFinalPass` answered black.
- Presets did not exist.

A scene that worked in the app could fail in the browser, and one written
in the browser could not use what the app offers. The browser has no
folder, no library path and no threads, so each piece has to come from
the page.

**Decision.**

- **Pictures go through the player's own image path.**
  - `ScenePlayer::replace_image(index, bytes)` decodes the bytes by their
    content and uploads them with the entry's flip, wrap, filter and
    mipmaps. The code is the same `upload_image` a file from a scene
    folder goes through, so the picture is the same texture.
  - The page's Add image keeps a PNG or JPEG under its own file name (4 MB
    at most). The sandbox matches an `IMAGES` path by its full name, then
    by its file name, since the page has no folders.
  - A picture the scene names but the page lacks reads black, as in the
    app, and is named under the editor.
  - The zip keeps every picture. A share link (fragment or short link) and
    the browser's storage carry them only while they come to 48 KB in all
    (`forSharing`), smallest first. Share names the ones it left out, so a
    link stays a link.
  - The Worker accepts the same 48 KB of base64 pictures. A scene without
    pictures keeps its old canonical form and so its old name.
- **`#include` resolves against the scene's own files**
  (`include::expand_files`). The lookup is the folder's: relative to the
  including file, then to the scene. `..` is resolved by name, and a name
  that climbs out of the scene finds nothing. The `#line` bookkeeping
  (D198) is shared, so an error still names the user's line.
  `SceneFolder::from_files` now takes owned text and expands includes as
  `load` does. There is no search path, so lygia and hg_sdf resolve only
  when the scene holds their files.
- **`textureFinalPass` is the app's readback** (D162).
  - The sandbox turns on `enable_final_pass_readback` for a script that
    names the function, as `Session::load` does.
  - WebGL2 cannot map a buffer. On wasm32, `Gl::read_buffer` reads the
    pack buffer with `getBufferSubData`, only after its fence has
    signalled, so it does not wait. The leaf is exempt from the
    driver-query count with that reason.
  - The page copies the 64x36 RGB picture into a buffer it allocated once
    (`Engine.finalPass`). It sends a copy with each frame message to a
    script that reads it. The worker's `textureFinalPass` samples it as
    `strobe-script`'s does: nearest texel, y up, clamped, black until the
    first read lands. Latency is the app's two frames, plus the worker's
    one.
- **Presets are `presets/<name>.json` files** in the scene, as in a scene
  folder, so the zip carries them to the app.
  - Save preset captures with `Preset::capture`, scene channel only, and
    the app's name rule (`valid_name`, mirrored in `validPresetName`).
  - Choosing a preset applies it with `Preset::apply`, as targets: a
    smoothed control eases.
  - A `default` preset is applied when a scene is opened, as the app
    applies its startup preset.
  - A preset's meta channel is ignored: the sandbox has no meta controls.

**Trade-off.**

- Cube maps and `MEDIA` stay app-only.
  - `MEDIA` decodes sequences on a thread (`Media::start`), and
    wasm32-unknown-unknown has none.
  - A cube map could take the same added-picture path as `IMAGES`.
    `load_cubemap` reads its faces from a folder, though, and the four
    pieces asked for were done first.
  - The page names both as not loaded. They are W-01's remaining work,
    with the Shadertoy audio texture and the meta controls.
- A share link can lose a large picture. The alternative was links of
  hundreds of kilobytes, or a picture store with moderation; D524 and
  D527 keep the site without one.
- A picture is held as base64 in the scene's JSON, a third larger than its
  bytes. It is decoded on every compile, which costs milliseconds for the
  sizes a link or storage keeps.

**Test.**
- strobe-scene:
  - `include` test `a_scenes_own_files_resolve_with_no_folder_behind_them`
    covers nested includes, `..` from the including file, each file once,
    the line numbers kept, and no escape from the scene;
  - `load` test `a_scene_from_files_reads_like_a_folder`.
- strobe-web (`tests/sandbox.rs`, headless GLES 3.0, CI's Linux job):
  - `an_image_the_page_adds_draws_as_the_scene_folders_file_does` and
    `an_include_resolves_against_the_scenes_own_files_as_in_the_app`
    require the same bytes as the app's `SceneFolder::load` and
    `ScenePlayer` for the corpus gate's `media-image` and `include-file`
    fixtures;
  - `a_script_that_reads_the_picture_gets_the_asynchronous_readback`;
  - `a_preset_captures_the_controls_and_brings_them_back`.
- Site unit tests:
  - `play-files.test.ts`: names, base64, `forSharing`, the share
    round-trip, zip round-trip with pictures and presets;
  - `script-worker.test.ts`: `textureFinalPass` sampling;
  - `scene-store.test.ts`: the Worker's picture limits and unchanged
    names.
- `tests/e2e/play-parity.spec.ts` in Chromium (SwiftShader), passing on
  LIGHTNING: an include, an added picture with the missing-picture note
  before it, a `textureFinalPass` script whose right half turns red from
  the read-back left half, and a preset saved and applied.
- The wasm path (`getBufferSubData`) is exercised only by that browser
  test; the native tests take the mapping path.

**Would reopen:** threads in the browser build, which would let `MEDIA`
run as in the app; a picture store behind short links, which would lift
the 48 KB; or a browser whose `getBufferSubData` waits even after the
fence.
