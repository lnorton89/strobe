# D545: shipping keeps fat LTO, sccache is dropped, and nextest waits for more runs (2026-11-04, engineering audit follow-up)

**Context.** D535 made sccache and thin LTO experiments, to be decided
from numbers, and piloted nextest on Windows. The Experiments workflow
could only run once it reached the default branch, which happened when the
audit stack merged. It was then run twice on master (4c7fca4): once cold
with the LTO comparison, once again for sccache's warm cache. The T480 had
already benched both LTO profiles (D544).

**Decision.**

- **Shipping keeps fat LTO.** The comparison, on a cold `windows-latest`
  runner (run 41917572704):

  | profile | build | `strobe.exe` |
  |---|---:|---:|
  | `release` (fat) | 677 s | 16,859,648 bytes |
  | `release-thin` | 517 s | 17,497,600 bytes |

  Thin saves 160 s (24%) for a 3.8% larger binary. On the T480 every
  scene's frame time was the same within about 1% (D544). Fat stays
  anyway, for two reasons:
  - The saving lands only where fat LTO is built: master's post-merge
    Windows job and a release. A pull request, and a developer's
    `release-fast` edit loop, never build it.
  - The bench measured GPU-bound frames. It did not measure the CPU-side
    paths that LTO could change (QuickJS scripts, audio analysis, the
    remote server).

  `release-thin` stays, for the Experiments workflow to measure again.
- **sccache is dropped.** The trial ran the Windows `check` and `test`
  lanes through sccache, backed by GitHub's cache, without rust-cache:

  | run | hits | clippy | tests | total |
  |---|---:|---:|---:|---:|
  | cold (41917572704) | 0 of 571 | 349 s | 612 s | 961 s |
  | warm (41920791981) | 536 of 571 (93.9%) | 148 s | 191 s | 339 s |

  The warm cache works, but it does not beat what ci.yml already does.
  The Windows job, warm through rust-cache, spent about 36 s on clippy and
  about 240 s on tests (nextest) on #87. Restoring the whole target folder
  makes clippy nearly free, where sccache still fetches every crate's
  output. 216 calls per run were not cacheable at all. The weekly trial
  is removed from `experiments.yml`; the LTO comparison stays there, on
  demand.
- **nextest is not decided yet.** The Windows test step, compilation
  included, took 157-254 s on warm runs and 415-588 s on runs whose cache
  missed. That is over 14 master and pull-request runs since the pilot.
  The same step under `cargo test` took 170-267 s on master before the
  pilot. That overlap is not a speed answer. D535 asked for a few weeks
  of the Windows job's JUnit times, and those exist only from today.
  Meanwhile nextest's other half has already earned something: running
  every binary's tests at once exposed two timing tests that share the
  machine badly (D544).

**Trade-off.** Fat LTO costs master's Windows job and each release about
2.7 minutes, for an unmeasured CPU-side benefit. Dropping sccache gives up
its potential on a cold rust-cache, which ci.yml's runs rarely see.

**Test.** The runs above. The Experiments workflow's LTO job still runs by
hand.

**Would reopen:**
- **LTO:** a CPU-side bench (scripts, audio) showing no difference, or the
  release build becoming a bottleneck.
- **sccache:** rust-cache misses becoming common enough that a per-crate
  cache would win.
- **nextest:** its JUnit times, over weeks, against the other jobs'
  `cargo test`.
