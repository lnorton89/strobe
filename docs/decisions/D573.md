# D573: Sharing works the way VJ tools do: saved, sized, blacked out, UYVY on the GPU, idle with no receivers

Date: 2026-11-26
Status: Accepted
Areas: output, app, gfx, native
Backlog: M-06
Related: D570, D571, D572, D135

## Context

D570 to D572 built the two senders and verified that Spout publishes. Before
taking M-06 further, its first cut was reviewed and compared with how the
tools people already use expose output sharing. The survey covered
Synesthesia, Resolume, TouchDesigner, MadMapper, OBS (DistroAV and the Spout2
plugin), vMix, Millumin, Magic and VDMX, plus the NDI SDK's licence and
performance pages, and is recorded in
[research/m06-ndi-spout.md](../research/m06-ndi-spout.md).

The review found faults in the first cut:

- **The Spout object leaked.** `GetSpout` builds a new object on every call,
  freed by its own `Release`, which was never called. The library was then
  unloaded under a live object that still held its Direct3D device and
  interop.
- **A resize called `CreateSender` again** rather than `UpdateSender`.
- **D572's slot explanation was wrong.** It said "the header is one slot out
  from the binary". In fact MSVC groups every overload of a virtual name at
  the first declaration's position, so `GetName(std::string)`, declared near
  the end, takes slot 7. That moves `GetName()` and everything after it, up
  to the overload's own declaration, one slot later. The slots are right; the
  reason was not.
- **The NDI path cost more than it had to.** Each frame made two full-size
  allocations in a synchronous readback that stalled the pipeline, a third
  allocation to clone the frame, and a synchronous send. The SDK's guidance
  is UYVY, converted on the GPU, sent asynchronously.
- **Toggling either sender rebuilt both**, and the per-frame apply allocated
  two strings every UI frame.
- **Two UI strings and one error string had broken line continuations**, so
  long runs of spaces were drawn inside them.
- **`grafton-ndi` sat in the Windows-only dependency table**, so the `ndi`
  feature did not build on Linux and CI's Linux check would have failed.
- **Nothing was saved**, names could not be edited, and the size could not be
  set.

## Decision

Sharing follows what the surveyed tools have in common, plus what the NDI
SDK asks of a sender:

1. **Settings > Output > Sharing is saved** (`SharingPref`): each sender on or
   off and its name, NDI's groups and frame-rate cap, and the shared size. The
   command-line flags `--spout`, `--ndi`, `--ndi-groups`, `--ndi-fps` and
   `--share-size` override it for one run. They change only the `live` copy,
   so a launcher's flags never overwrite the operator's choice.
2. **Names are editable** in Settings. Enter or a click away applies the new
   name; a blank name is ignored.
3. **The shared picture follows blackout.** Synesthesia and Resolume share
   the final composition, so a receiver on another screen goes dark with the
   projector. This reverses D570's "a receiver keeps its feed". A receiver
   that wants the feed kept is the exception, and can be served later by a
   second sender (see nice-to-haves).
4. **Size: the picture's own, or fixed.** This is Synesthesia's "Constant
   Output Resolution". A fixed size draws the picture once, scaled, into the
   share stage's own target. At the picture's own size, and not blacked out,
   Spout shares the picture's texture directly, with no draw at all.
5. **NDI gets UYVY packed on the GPU** (`strobe_gfx::share::ShareStage`):
   - Each texel of a half-width RGBA8 target holds one UYVY pair (BT.709,
     limited range), in the same equations `strobe_output::pixel` tests.
   - Rows are written top first, so the CPU turns nothing over.
   - The target is read back through a ring of three pixel-pack buffers
     behind fences. The oldest read is collected only once its fence has
     signalled, so the frame never waits; the picture is two frames late.
   - Frames go out with `submit_video_copy` (async). In steady state nothing
     is allocated.
   - `tests/render.rs` checks the packing byte by byte against the reference,
     in both dialects, on Mesa.
6. **No receivers, no work.** NDI's connection count is polled twice a
   second. While it is zero, nothing is packed or read back; NDI hands a new
   receiver the last frame. An optional cap (60, 50, 30 or 25 fps) limits how
   often a frame is packed.
7. **Status and licence.**
   - The Spout row shows what is going out: name, size, receivers and the
     measured NDI rate. Each sender's failure appears on its own row.
   - A missing NDI runtime gives one short line with a link to
     ndi.video/tools. The loader's list of every folder it tried goes to the
     log.
   - NDI's trademark line and a link to ndi.video sit beside the choice and
     in About, as NDI's licence requires.
8. **Spout's object is released.**
   - `Release` (slot 174) is called from `Drop`, after `ReleaseSender` and
     before the library is unloaded.
   - A resize calls `UpdateSender` (slot 71).
   - Every slot is pinned to the one `cl` itself emits for a call through the
     2.007.018 header.
9. **The GPU half lives with the context.** The stage and the Spout sender
   sit in the app's context stack (`GpuShare`) and are torn down with it. On
   a lost context the Spout sender is leaked rather than released, because
   releasing it would call into a dead context. A rebuilt context opens Spout
   again.

Not taken, recorded in the research page's list:

- NDI audio.
- Alpha (nothing produces it until D248 does).
- 16-bit output.
- Several senders (a clean feed beside the post feed).
- NDI delay, failover and tally.
- OSC control of sharing.

## Consequences

- NDI on a laptop with no receiver connected costs nothing beyond a counter
  poll. With a receiver, it costs one half-width draw, an asynchronous copy
  of half of RGBA's bytes, and a memcpy.
- Spout at the picture's size is still zero-copy. At a fixed size, or in
  blackout, it costs one draw.
- Verified on LIGHTNING:
  - `--spout StrobeCheck --share-size 1280x720` is listed by an independent
    receiver-side probe at 1280x720 BGRA with a live handle.
  - The sender is gone from that list after a clean exit, which exercises
    `Release`.
  - Without an NDI runtime, `--ndi` gives the one-line note and the show
    runs on.
  - Later the same day, with NDI 6 Tools 6.4 installed, an independent
    NDI receiver found `--ndi "Strobe NDI Test" --share-size 1280x720`,
    had its first 1280x720 frame 0.43 s after connecting, and received
    56 frames a second, the show's rate. The saved frame is the scene,
    with the right colours.
  - A receiver built on the Spout SDK's `ReceiveImage` read both Spout
    feeds' pixels. Blackout over OSC turned the main feed black and left
    the clean feed alone, and Spout and NDI carried the same upright
    picture.
  - With no scene playing, both senders now send black; before, an NDI
    receiver that connected first got no frames at all.
  - OBS Studio 33 (win-spout 1.15.0, DistroAV 6.2.2) shows the Spout main,
    Spout clean and NDI feeds side by side, upright. On a still test card,
    OBS's NDI and Spout pictures agree within one level, so the limited
    range UYVY decodes correctly. Blackout and the output's invert reach
    the main and NDI feeds in OBS and not the clean feed.
- Still not verified: NDI to a second machine, the NDI cap's rate on a
  quiet machine, and the frame cost on the T480 (M-06's acceptance).
