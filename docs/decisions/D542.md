# D542: the library's scenes are prerendered at launch and on a rescan, on by default (2026-11-03, owner's request)

A library scene's first load compiled its shaders, started its script and
read its images on the thread that draws the output: 30-130 ms on the AMD
desktop (LIGHTNING), a visible stall each time a scene was played for the
first time in a run. A playlist already avoids this with its precompile
(D151); the library had nothing.

- **What prerendering does.** At launch and whenever the library is
  listed again, every scene not already prepared is loaded at 1x1, drawn
  once (`Session::prime`, so the driver finishes what it defers to the
  first draw) and parked in `Stack::prerendered` (`prerender::Prerender`).
  Loading a parked scene is a resize and a restart: passes rebuilt from
  black, controls back to the scene's start, script started over, clock at
  zero, as a fresh load leaves it. Measured: 1-3 ms, against 77 ms for the
  same scenes loaded fresh.
- **One scene a step, never during a show.** A step blocks for that
  scene's compile, as a playlist's precompile does, with at least 50 ms
  between steps so the output draws in between. Nothing is prerendered
  while a playlist is loaded (its precompile and cues come first), a load
  is waiting, the context is being rebuilt, or a screenshot is being
  taken. 112 scenes took 11-13 s at launch.
- **Parked lean.** A parked scene keeps its programs, images and script,
  and lets every render target go, `FIXED_SIZE` and literal-size passes
  included (`ScenePlayer::release_targets`): it restarts from black when
  it plays, so their contents are worth nothing. Keeping them cost about
  29 MB a scene (3.3 GB for 112); without them, about 5 MB a scene (from
  133 MB to 732 MB private for 112, debug build).
- **Never stale.** A parked scene carries a stamp of its folder (files,
  bytes, newest change) taken before it was read, and is used only while
  the folder still matches; otherwise it is dropped and the scene loads
  fresh. An edit in the Editor or outside Strobe is never hidden.
- **The scene being replaced is parked too,** so going back to it costs
  nothing. A rescan prerenders only what is new and drops what left the
  library. A context rebuild drops everything with the context and plans
  again.
- **Broken scenes are found early.** A scene that does not load while
  prerendering is marked broken in the browser, as a load by hand marks it.
- **On by default; Settings > Output > Prerender scenes** turns it off
  (every parked scene is let go) and on (planned at once), saved in
  `ui.toml` (`[prerender] enabled`). `--no-prerender` turns it off for one
  run without changing the setting.

**Evidence:** `prerender` tests
`a_plan_queues_what_is_not_parked_or_live_and_drops_what_is_gone` and
`a_parked_scene_is_handed_out_only_while_its_folder_is_unchanged`;
`render.rs` `a_parked_player_whose_targets_were_released_plays_again_from_black`
(headless GL, both dialects; skipped where there is none);
`ui::state` `the_prerender_switch_is_on_by_default_saved_and_reread_but_its_note_is_not`;
the `prefs` round trip; and a run on LIGHTNING: 112 scenes prerendered in
12.6 s, then four scenes stepped over OSC loaded in 1-3 ms each, logged as
prerendered.

**Would reopen:** memory on the HD 4000 laptops (T480 check: a large
library's prerendered set against the machine's RAM, which may want a
cap), a scene whose script or images make parking expensive, or
`GL_KHR_parallel_shader_compile`, which could take the compile off the
frame loop entirely.
