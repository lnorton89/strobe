# D566: local time comes from jiff, not chrono (2026-11-21, to clear RUSTSEC-2026-0543 from CI)

**Context.** RUSTSEC-2026-0543 marks `chrono` unmaintained, every version,
with no fixed release. `cargo deny` fails on it, so every branch's CI went
red at once, master's included. Strobe used `chrono` for two things only:
the UTC offset behind `strobe_Date` (D112) and the projector command log's
timestamps (D502). Nothing else in the tree pulls it in.

**Decision.** Both go through `jiff`, one of the advisory's two named
replacements, rather than an `ignore` entry in `deny.toml`: there is a
maintained crate to move to, and `deny.toml` keeps its ignores for crates
with none (D530).

- `localtime::system_offset_seconds` is
  `TimeZone::system().to_offset(now).seconds()`, with `now` built from
  `SystemTime` by `Timestamp::try_from`, so a clock `jiff` cannot represent
  reads as offset 0 instead of panicking. A zone `jiff` cannot find reads as
  UTC, as `chrono` did. The lookup still runs only in `LocalDate::refresh`,
  never on the frame path.
- The projector log formats `%Y-%m-%dT%H:%M:%S%z` as before, so existing
  `commands.log` files keep one shape.
- Features: `std`, `tz-system`, `tzdb-zoneinfo` (Unix's `/usr/share/zoneinfo`)
  and `tzdb-bundle-platform`.

**Cost.** Windows has no IANA database of its own. `jiff` reads the zone's
Windows name and needs a database to turn it into an offset, so
`tzdb-bundle-platform` embeds one in `strobe.exe` on Windows only, a few
hundred KB. Without it every Windows machine would read as UTC, which is
the bug D112 fixed. `time`, the other replacement, is already in the tree
through `rosc`, but its `current_local_offset` refuses in a process with
more than one thread on Unix, and the app always has several.

**Would reopen:** `jiff` dropping Windows zone lookup or the bundle growing
large enough to matter on the release zip; or a reason to read the offset
from Windows directly, which would need a new `unsafe` leaf outside the two
allowed modules.
