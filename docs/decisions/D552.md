# D552: the website and its wasm engine are built and played in CI, as a lane of their own (2026-11-05, backlog W-03)

**Context.** The `/play` sandbox (D524) is the app's scene player
compiled to wasm, and the site is built from the repository (D523). CI
ran strobe-web's native tests and, since D544, clippied strobe-web for
`wasm32-unknown-unknown`, but nothing ran `wasm-bindgen`, built the site
or opened `/play`. A change to the renderer, the scene model or the page
could break the website, and the first to know would be the next deploy
from a developer's machine (D525).

**Decision.**

- **A `site` lane in `cargo xtask ci`**, so the commands live in
  `crates/xtask/src/ci.rs` like every other job's (D533): `npm ci`, lint,
  typecheck, the unit tests, `npm run build` (whose `prebuild` builds the
  engine and binds it), the Playwright Chromium install and
  `npm run test:play`. Each is `npm --prefix site` from the root, the
  commands a person types in `site/`. It runs on any host. Without npm it
  is one `MISSING` step; the build is `MISSING` without the wasm target,
  or when `wasm-bindgen` is absent or is not the version Cargo.lock pins.
  The lane is part of `all`.
- **A `site` job in ci.yml runs that lane on Linux** and is part of
  `ci-ok`. The `changes` job gives a second verdict, `site`. It is true on
  every push, release run and manual run. On a pull request it is true
  when the change touches `site/`, `scenes/`, strobe-web, strobe-gfx,
  strobe-scene, strobe-audio, `Cargo.toml`, `Cargo.lock`,
  `rust-toolchain.toml`, `crates/xtask/src/ci.rs` or the workflow.
  `ci-ok` expects the job to pass when the verdict is true and to be
  skipped when it is false, so a docs-only pull request and a change
  elsewhere in the app still pass without it.
- **Every tool is pinned.**
  - `wasm-bindgen` is 0.2.129, the crate's version in Cargo.lock,
    installed prebuilt and checksummed by the pinned `install-action`. A
    conventions test (`toolchain`) fails when the workflow and the lock
    disagree, and `build-engine.mjs` refuses any other CLI.
  - Node is the release in `site/.nvmrc` (26.11.1), through
    `setup-node` at a full SHA.
  - Playwright is the version package-lock.json holds; `npm ci` installs
    exactly that lock.
  - `build-engine.mjs` now builds `--locked`, as every cargo command in
    CI does (D521).
- **Fast.** npm's download cache is keyed by the lockfile, the cargo
  cache has its own key (`site`), and Chromium's headless shell alone is
  installed (`--only-shell`), cached by the Playwright version. Only the
  `/play` spec runs, in one Chromium project. The job does not clippy:
  the Linux job's `check` lane already does.
- **The wasm clippy names strobe-gfx.** The `check` lane's `clippy wasm`
  step is now `-p strobe-web -p strobe-gfx --no-default-features
  --target wasm32-unknown-unknown`. Clippy already linted strobe-gfx's
  library on the way to strobe-web; naming it says so.
  `--no-default-features` keeps `native` off for it.
- **The smoke test, `site/tests/e2e/play.spec.ts`.**
  - A library scene (`?scene=02-plasma-pulse`) compiles, its controls
    come back, and the canvas draws more than black.
  - A shader error in the new-scene starter is shown as `main.glsl:2`,
    marks the file's tab and underlines the line in the editor, and the
    last good picture stays.

  Chromium is asked for SwiftShader (`--use-angle=swiftshader
  --enable-unsafe-swiftshader`). A runner has no GPU, and Chromium no
  longer falls back to software WebGL on its own. The same rasteriser on
  every machine also keeps the test off the desk's driver.

**Trade-off.**

- The rest of the site's Playwright suite (axe in both themes, overflow,
  navigation, the screenshot specs) does not run in CI. Its screenshot
  baselines are not committed (site/.gitignore) and it takes minutes; the
  sandbox is what the crates can break. W-03 keeps it as a question.
- A pull request that touches only the docs the site renders
  (`docs/USER_GUIDE.md` and others) does not build the site. D531 keeps
  docs-only pull requests cheap; a push to master builds it.
- Deploys are still run by hand (W-03).

**Test.**
- xtask `ci` tests:
  - `the_site_lane_builds_the_engine_and_plays_it_on_every_host`;
  - `the_engine_needs_the_wasm_target_and_the_locked_wasm_bindgen`;
  - `the_wasm_clippy_names_the_browser_crates_without_native`.
- strobe-conventions:
  `the_wasm_bindgen_cli_ci_installs_is_the_one_cargo_lock_pins`.
- `cargo xtask ci --strict site` on LIGHTNING (Windows) passed every
  step, the two `/play` tests included, in 75 s with a warm engine
  build.
- The pull request's own `site` job.

**Would reopen:** a deploy from CI (W-03), which would build in that
job; the whole e2e suite earning its minutes there; or Chromium dropping
SwiftShader, which would need a GPU runner or another software
rasteriser.
